# Agent Note: 可移植的插件故障安全网：将 DSH 的插件冲突与启动错误恢复机制提炼为一个可复用插件

Status: proposed

[English](2026-08-18-portable-plugin-failsafe.md) | 中文

## 问题

DSH 自动处理两类插件生命周期风险——与内置产品冲突的用户安装、导致启动失败的插件——而该机制分散在三处：

- **安装/更新时的冲突处理**位于 `packages/host/plugin-installer`：`disableControlsOnInstall` 规则在匹配的安装或更新后禁用内置产品的补丁行；bundle 行合并会跳过 profile 补丁层已认领的 insert 行 id，因此两套组件永远不会双重挂载。
- **启动错误的检测、归因与恢复**位于桌面壳（`apps/desktop/src/recovery.ts`、`boot-marker.ts`、`main.ts`）：启动生命周期标记、60 秒看门狗、确定性归因、有界的按插件失败环，以及恢复对话框阶梯（禁用并重启 / 安全模式 / 退出）。
- **结构性基座**是带归属标记的受管行所在的 profile 补丁层（`packages/host/plugin-installer/src/patch.ts` 与 `bundle.ts`）、`packages/boot/app-boot` 中的 fail-loud 激活审计，以及 `apps/cli/src/profile-boot.ts` 中以 `skipUserPatches` 实现的安全模式。

想要同样安全网的第三方项目目前必须从三处逆向还原这套机制，且壳层代码无法直接带走。本笔记把机制提炼为原理，并提议将其打包为一个可安装、与宿主无关的插件。

## 提案

### 机制提炼

**原理一——冲突在写入时结构性消解，而非运行时仲裁。** 由一张补丁层统一持有「挂载什么、是否启用」：每个条目有稳定 id，层内只有两种行语义——按 id 定向覆盖（后写生效）与 `insert` 列表（新增条目）。每次修改都携带归属标记注释（`dsh-plugin-installer: <id>`、`dsh-plugin-control: <id>`、`dsh-plugin-bundle: <id>`），因此行可审计、可移除、可由其所有者再次翻转。双重挂载在写行时被阻止，而不是在条目启动时仲裁：bundle 合并跳过已被认领 id 的 insert 行，配置的冲突规则（web profile 中的 `disableControlsOnInstall: [{ id: 'web-ui', matches: ['dsh-web-ui'] }]`）禁用重复内置产品的行。因此每个自动冲突动作都是可逆的（把同一批行翻回来即可）且可归因的（标记写明了操作者）。

**原理二——错误走一条有界的「检测 → 归因 → 处置 → 留证」闭环。** 检测覆盖三种任何单一机制都抓不住的失败形态：抛出的加载/激活失败（Loader 的激活审计点名每个失败条目并 fail-loud）；启动挂起（看门狗超时）；硬崩溃或主线程挂起（启动标记：写了 `started` 却没有后续的 `ok`，外加 `bootAttempts` 连续计数）。归因是确定性且保守的：加载失败归咎于失败文本中出现名字的已装插件，挂起归咎于上次成功启动之后安装或更新的插件，其余情况不给责任名单——乱猜不如不猜。写时规则未能预防的冲突同样进入这条闭环：它与任何插件错误一样表现为启动失败，由同一阶梯处置——不存在另一条冲突恢复路径。处置阶梯按置信度逐级下探：可归因 → 记录并给出「禁用相关插件并重启」（与用户开关共用同一个受管行写入器）；不可归因 → 给出安全模式（跳过用户补丁层且不做解析——损坏的补丁文件是恢复场景，不是启动阻塞）；安全模式仍失败 → 内置或安装问题，重试或退出，绝不因此禁用用户插件；连续三次失败 → 安全模式成为默认选项。留证在构造上有界：按插件一环（每插件一条、新覆盖旧）、硬上限（8 条记录、2 KB 摘要、16 KB 栈、100 KB 整文件）、读写时清扫的 90 天保留、原子写入，卸载或成功重新启用时清除。修复面是失败徽章、复制错误与「让 Agent 修复」——以插件安装根为工作区的会话。

**原理三——单一权威、单一写入器，诊断永不阻塞恢复。** 安装状态、失败记录与补丁行全部经由一个串行化、文件锁、原子写的网关变更；恢复复用设置开关使用的同一个写入器，因此任何格式都不存在第二份实现。配置错误在启动时 fail-loud（存在但无法应用的补丁文件是错误，绝不被跳过），而诊断按路径降级（损坏的失败环绝不能阻塞启动恢复；读取时 fail-loud 以供修复）。真实启动是唯一的权威冲突与失败检测器——不信任任何预检启发式。

### 可移植插件

把机制打包为一个可配置插件（暂定名 `dsh-plugin-failsafe`），宿主差异收敛为五个适配器端口，目标项目通过实现端口接入，而不是分叉整套机制。

- `PluginRegistry`——已安装插件（id、名称、版本、installPath、installedAt）：归因输入与修复上下文。
- `EnableWriter`——持久化单个插件的下次启动启停（DSH：受管补丁行的 `disabled` 标记）；宿主自己的用户开关必须使用同一端口。
- `BootControl`——启动标记读写、看门狗包装、重启，以及安全模式开关（DSH：`skipUserPatches`）。
- `Reporter`——恢复对话框、失败徽章与日志出口（桌面对话框成为其中一个实现）。
- `Store`——home 目录下的文件原语与原子写（有界失败环、标记）。

配置面，全部带默认值并匹配桌面行为：`bootTimeoutMs`（60 秒）、`consecutiveFailureThreshold`（3）、失败环上限与保留期、`conflictRules: [{ id, matches }]`，以及可选的归因钩子（替换「名字出现在失败文本」与「上次成功启动之后安装」两个默认归因）。

行为契约——每一步何时执行：

| 生命周期时点 | 动作 |
| --- | --- |
| 启动开始 | 写入 `started` 标记，读取安全模式，清扫过期失败记录 |
| 启动中 | 在看门狗下运行宿主启动；成功后写入 `ok` 并清除已重新启用插件的失败记录 |
| 启动失败 | 归因 → 记录 → 报告器阶梯（禁用+重启 / 安全模式 / 退出；安全模式仍失败分支） |
| 运行期 | 宿主 fail-loud 钩子 → 记录可归因的迟到拒绝 |
| 安装/更新成功 | 应用冲突规则 → 禁用重复的内置产品 |
| 卸载/重新启用 | 清除该插件的失败记录 |

目标宿主的移植清单——最小假设：支持按插件持久化、下次启动生效的启用/禁用；有插件 id 与安装时间；有一个明确的「启动已 ok」时点与 fail-loud 退出；有重启通道。可静默并进程内重试的热替换宿主是延期扩展——见下方被否决的同进程容错方案。

交付形态：在 DSH 中作为普通插件（plain 或 bundle）安装，用适配器实现替换桌面专属部件；对其他项目，同一核心随宿主适配指南发布，五个端口是唯一的宿主专属代码。

## 备选方案

- **同进程容错（把失败条目以禁用状态挂载并继续运行）。** DSH 已否决：需要改动 vendored Loader 的事务回滚语义，并容忍插件在 `apply` 中途抛错后的半注册服务；禁用-重启复用了既有重启通道。可移植插件保持同样的「下次启动生效」边界。
- **Agent 驱动的安装时冲突预检。** 否决：安装前对插件代码的解读是非权威信号；真实启动才是权威冲突检测器，恢复流程已把它的裁决交给用户。
- **只追加的错误日志。** 否决：无界增长需要后台清理任务；失败环在每次写入时有界，并靠生命周期事件清理。
- **无对话框的全自动禁用。** 否决：用户拥有代码执行决策权并需要可见性，且安全模式是归因永远无法自行选择的选项。宿主仍可选择 `autoDisable` 策略，但不是默认值。
- **按宿主逐一复制机制。** 否决：壳、安装网关与启动胶水是三个耦合面；五个适配器是最小宿主专属面，并把不变量保留在唯一一份实现中。

## 验收标准

- 在 DSH 上，插件复现当前桌面行为——冲突规则禁用、标记/看门狗/归因、失败环、恢复阶梯、安全模式、成功与卸载时的清除——桌面对话框作为其中一个 `Reporter` 实现。
- 至少一个非 DSH 测试宿主（演练五个端口的夹具宿主）跑通完整闭环：安装冲突 → 自动禁用；强制加载失败 → 归因 → 禁用 → 重启；挂起 → 挂起嫌疑名单；不可归因 → 安全模式；成功重新启用 → 记录清除。
- 每个可调项都有文档化的默认值且匹配 DSH 行为；默认闭环不需要任何配置。
- 有界失败环与原子写不变量在夹具宿主下成立（上限、保留期、损坏文件行为）。
- README 与宿主适配指南记录五个端口、行为契约与移植清单。

## 风险

- 归因仍是启发式：同时安装多个插件可能过度禁用。安全模式是文档化的兜底——DSH 已接受同一取舍。
- 硬崩溃与主线程挂起不留记录；只有启动标记覆盖它们。无法在启动时写标记的宿主会失去该分支。
- 没有「下次启动生效」边界的宿主（纯热替换系统）适配较差；插件先面向基于重启的宿主，进程内扩展记录为延期。
- 安全模式整体跳过用户层，可能掩盖内置缺陷；「安全模式仍失败 → 安装问题」分支保证两类原因可区分。
